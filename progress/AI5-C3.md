## 1. 数据来源与限制(必读)

### 1.1 真实 Trace 不够用

- `Trace.Record` 把每轮轨迹写在 `$TIPCL_HOME/cache/ai_trace/YYYYMMDD.jsonl`,保留 14 天。
- 本机实测:全盘只找到 **110 个 `ai_trace` 目录**,全部位于 `%TEMP%\tipcl-tests-*` / `%TEMP%\tipcl-selftest-*` 之类的临时 `TIPCL_HOME` 下(自检与单元测试产生),共 373,004 B / 110 个 jsonl,**没有一条真实用户回合**。
- 本分支的 Linux 代码里 `grep -r "tool_schema_miss"` **零命中**(那是 C2 包的内容,还没做)。Windows 树的 `tool_schema_miss` 也只在本机跑过测试,没有真实分布数据。

→ 所以「`tool_schema_miss` 的出现率(每百回合)」只能给**代理指标**,口径见 §1.2。任务书也允许这么做(「真实数据不够时,用一份 30-50 条的典型请求集离线回放」)。

### 1.2 代理指标的定义(重要)

- **一轮** = 一次用户请求(一次 `SelectToolSchemas` 调用对应的那一回合)。
- 每条请求都**人工标注**「本轮必须能被调用的工具集 `ideal`」(依据:`AiData.SYSTEM_PROMPT` 里写明的流程 + 工具语义;多轮请求标注的是**最后一轮**).
- **漏选** = `ideal` 里有工具不在本轮下发列表里。这正是 C2 要抓的 `tool_schema_miss` 的成因:模型要调它,但它没在 `tools` 里 → 用全量表重发一次。
- **漏选率(每百回合)** = 有漏选的请求数 ÷ 有标注的请求数 × 100(近似「每百回合出现几次」)。
- **token** = 项目自己的估算口径(`Tokens.EstimateText`:CJK 1 / 其余 0.25),对每个 tool schema 的 JSON 序列化求和;报的是 **tools 部分**,不含系统提示与历史。
  - 同一口径下:系统提示 2955 token、全量 78 个工具 13770 token、`CORE_TOOLS` 18 个 2243 token —— 与 a1 报告记的「系统提示约 5.0k / 18 个常驻工具约 2.1k / 78 个全发约 12.0k」量级一致(前两项差异是两套估算口径,不影响本报告内的相对比较)。
  - 这是**估算**,不是计费真值;差异在同一个方向、同一个量级,用来比方案是够的。
- **往返成本**:流式接口每多发一轮请求都要把「系统提示 + 全部历史 + tools」重发一遍。本报告按「系统提示 + 消息」实测 ≈ 2982 token/轮(典型集)作为一次额外往返的输入成本。
  - 注意:如果 provider 有 prompt caching,重发部分按缓存价计费,这一项的权重会下降(§4.3 有敏感度)。

### 1.3 请求集是怎么造的

- **典型请求集 40 条**:覆盖装模组 / 光影 / 材质 / 数据包 / 地图、启动排错、卡顿优化、存档备份还原、版本升级、整合包造包导出、服务器、联机、账号皮肤、布局、配置、日志文件,以及 4 条多轮续话(含场景 19 的变体);1 条「你好」作为无标注对照。
- **口语变体集 12 条**:同一批意图换一种常见口语说法,专门用来量「漏选率对说法有多敏感」。
- 多轮请求在回放时按真实形状装配历史:`system` → 上一轮 `user` → `assistant` → `tool`(带一段像真实工具回填的 JSON)→ 本轮 `user`。工具结果的文本也算进关键词窗口(C1 之后如此,和 Windows 一致)。
- 每条请求的 `ideal` 都在报告里列出来,便于复核与后续验收复用(§2)。

- **口语变体集 41.7/百回合 vs 典型集 17.9/百回合**:同一个意图换个说法就掉工具(「禁用」→「停用」/「别加载了」、「卸载」→「卸了」、「导出报告」→「整理一下发给作者」、「写文件」→「建个文件写点说明」)。这说明**关键词表的缺口不是"少一两个词",而是覆盖的是书面语**;方案 1 如果只补「当前抓到的这几个词」,下一批新说法还会漏(参见 V01 vs V02:「停用」漏、「关掉」因为命中 ACTION_RE 而侥幸过关)。
- **注意 R10 与 V02 的对照**:同一个意图,只要命中 `ACTION_RE`(「关掉」在表里),写工具就会被全带上、不漏;换个说法(「停用」/「提问式」)就漏。也就是说,现在的兜底是「要么靠关键词,要么靠把 33 个写工具全倒进来」,中间没有台阶。

### 4.3 不能只看「常驻表」:多发一轮的往返成本

漏选和「按需加载」都会让这一轮**多一次请求**,而每次请求都要把「系统提示 + 全部历史 + tools」重发一遍(实测 ≈ 2982 token/轮,且这还没算第二轮模型输出与延迟、没算用户多等一轮)。

| 口径 | 频率 | 单位成本 | 每百回合 |
|---|---|---|---|
| 现状:漏选 → C2 用**全量表**重发一次 | 典型集 17.9/百回合(7 条请求、8 个工具) | 8850(tools 差值)+ 2982(上下文)≈ 11.8k | **≈ 21.2 万 token** |
| 现状(变体集) | 41.7/百回合(5 条请求、6 个工具) | 9383 + 2980 ≈ 12.4k | **≈ 51.5 万 token** |
| 方案 2:需要非 CORE 工具的轮次多一次 `load_tools` 往返 | 典型集 37/40 = 92.5/百回合 | 2982(上下文;tools 常驻部分本来就小) | **≈ 27.6 万 token** |
| 方案 2(变体集) | 12/12 = 100/百回合 | 2980 | **≈ 29.8 万 token** |

**净账(典型集,每百回合)**

- **方案 1a**:常驻多花 9.2% × 5150.8 × 100 ≈ **+4.7 万**;消掉 8 次漏选重发 ≈ **−21.2 万** → **净省约 16.5 万 token/百回合**(还少 7 次往返延迟)。
- **方案 1b**:常驻 **+0.2 万**;如果关键词补得全(把 §3.2 那 6 类说法全覆盖,漏选降到 0)→ **净省约 21 万**。补不全则按补齐比例打折。
- **方案 2**:常驻省 19.9% × 5150.8 × 100 ≈ **−10.3 万**;但加载往返 **+27.6 万** → **净多花约 17.3 万 token/百回合**。
  - **敏感度**:若 provider 有 prompt caching,重发的上下文按约 1/5 计价(27.6 万 → 约 5.5 万),方案 2 就是**净省约 4.8 万/百回合**;若缓存完全未命中,则净多花 17.3 万。**这个结论直接取决于缓存计价与命中率,本机没有真实账单数据可验。**
  - 另外:方案 2 的目录可以让模型**更少猜关键词**(漏选理论上归零),以及一次 `load_tools` 可以批量加载多个工具 —— 这两个方向都会降低往返次数,但都不会降成 0(首轮总要加载一次)。

### 4.4 两方案的非 token 取舍

| 维度 | 方案 1(补关键词 / 并入 CORE) | 方案 2(一行目录 + find_tools/load_tools) |
|---|---|---|
| 实现面 | 改数据表(关键词表 / CORE 列表),1 个文件,零新工具 | 新增 2 个工具 + 目录生成 + 加载状态管理(哪些 schema 已在本轮上下文里)+ 系统提示要写「先找工具再干」的规矩 |
| 漏选率 | 补到的降到 0,没补到的照旧(口语多样性是长尾) | 理论上归零(目录里什么都有) |
| token | +0.4% ~ +9.2%,无额外往返 | 常驻 −19.9%,但每轮多一次往返(92.5% 的轮次) |
| 延迟 | 不变 | 每轮多 1 次模型往返(用户可见的"慢一拍") |
| 与 C2 的关系 | 仍然需要 C2 兜底 | 仍然需要 C2 兜底(模型也可能不看目录) |
| 风险 | 表只会变大,写工具误带的概率略升(1a 把 `delete_mod` 常驻) | 目录必须与 schema 保持同步;`load_tools` 的结果进上下文后要算进压缩预算 |
