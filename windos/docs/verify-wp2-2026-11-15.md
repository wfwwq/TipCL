## 1. R1:Windows 测试工程的隔离缺陷 —— 已修

### 1.1 根因(实测,不是推测)

`Utils.ROOT` 是**惰性缓存的静态量**(`Core/Launcher/Utils.cs` 的 `ROOT` 属性),只有
`ResolveRoot()`(`:309-322`)才每次都去读 `TIPCL_HOME`。而 `windos/tests/TipCL.Tests/TestHome.cs`
此前**只设环境变量、从不调 `Utils.SetRoot()`** —— 进程里任何一处先碰到 `Utils.ROOT`,根就钉死
在那一刻的取值上,之后每个 `TestHome` 都是空操作。Linux 侧 `tests/TipCL.Tests/TestIsolation.cs`
用 `[ModuleInitializer]` + `Utils.SetRoot(dir)` 兜住了这个坑,Windows 侧缺这一层。

修复前的定向复跑(4 条新守卫,`--filter FullyQualifiedName~TestIsolationTests`)**3 红 1 绿**,
失败原文里同时暴露了两条取根路径分家:

```
Utils.ResolveRoot() 指向真实用户目录,测试会读写用户数据:C:\Users\Administrator\AppData\Local\TipCL
TestHome 之后 Utils.ROOT 没跟着走:先读到的是 ...\temp\tipcl-test-dc403597...,
  现在是 ...\temp\tipcl-test-dc403597...,期望落在 ...\temp\tipcl-test-63f9a32d...
```

第一处是"没有 TestHome 时根会落到真实用户目录";第二处是"根被钉住之后 TestHome 失效"。
两者都是 R1 的同一根因,且都被这条用例钉成了可复现的红。

### 1.2 改法(只在测试工程内)

| 文件 | 改动 |
|---|---|
| `windos/tests/TipCL.Tests/TestIsolation.cs`(新增) | `[ModuleInitializer]`:建进程私有临时根 → 设 `TIPCL_HOME` → `Utils.SetRoot(dir)` → `ProcessExit` 清理 |
| `windos/tests/TipCL.Tests/TestHome.cs`(+8 行) | 构造时 `Utils.SetRoot(Dir)`,释放时 `Utils.SetRoot(_old)` 交还环境变量解析 |
| `windos/tests/TipCL.Tests/TestIsolationTests.cs`(新增) | 4 条回归守卫(见 1.3) |

**产品代码一行未改。**

### 1.3 守卫用例(为什么这样写)

- `ProcessRootIsNotTheRealUserDataDir`:不建 `TestHome`,直接断言 `Utils.ROOT` 与
  `Utils.ResolveRoot()` 都不在 `%LOCALAPPDATA%\TipCL` 之下 —— 验的是"进程级兜底"。
- `RootFollowsTestHomeEvenIfRootWasReadEarlier`:**先读一次** `Utils.ROOT` 再建 `TestHome`
  再断言根跟着走 —— 刻意复现真实序列(别的测试类/产品静态初始化先碰到 ROOT)。
- `ResolveRootAndCachedRootAgreeInsideTestHome`:两条取根路径必须一致(产品里两条都在用,
  例如 `Core/Launcher/Sync/PhoneLink.cs:58` 的 `StatePath` 走 `ResolveRoot()`,其余多数走 `ROOT`)。
- `JsonWritesLandInIsolatedRootNotInRealUserDir`:在隔离根里放哨兵 `config.json` +
  `Utils.WriteJson` 写探针;**写之前先断言根在隔离目录里**,红了就在写之前红,绝不允许测试自己
  往真实用户目录写文件。

## 4. Windows CI 的两个失败:一个新的已定位,一个仍是假设

### 4.1 已定位(证明):`ci-windows.yml` run #8 的 10 条断言 = CRLF 结帐 vs LF 打包

- run #8(id `43603980639`,sha `335cb3c`,2026-11-14T14:16Z)是 `CI`(ci-windows.yml)历史上**唯一**一次红;
  失败步骤 `单元测试`,注解是 10 条 `TipCL.Tests.CoreResourcesPackTests.EmbeddedResourceMatchesSourceFile`。
- 该用例断的是「内嵌资源解压后的字节 == 源文件字节」(`CoreResourcesPackTests.cs:63`)。
  CI 上报的 `Expected`(源文件在 runner 上的长度)与 `Actual`(内嵌解压长度)之差,**逐文件等于该文件的行数**:

| rel | CI Expected | CI Actual | 本机源文件长度 | 本机 LF 数 | 长度+LF==Expected |
|---|---|---|---|---|---|
| ai/model_rules.json | 41543 | 39748 | 39748 | 1795 | ✔ |
| plugin-host/host-web.mjs | 21237 | 20820 | 20820 | 417 | ✔ |
| plugin-host/sdk.js | 13961 | 13638 | 13638 | 323 | ✔ |
| plugin-host/host.mjs | 13034 | 12758 | 12758 | 276 | ✔ |
| plugin-host/tipcl-plugin.d.ts | 13761 | 13513 | 13513 | 248 | ✔ |
| plugin-host/host-util.mjs | 8451 | 8273 | 8273 | 178 | ✔ |
| plugin-host/host-sessions.mjs | 4310 | 4209 | 4209 | 101 | ✔ |
| plugin-host/sdk-events-worker.js | 2523 | 2458 | 2458 | 65 | ✔ |
| plugin-host/host-loader.mjs | 1357 | 1328 | 1328 | 29 | ✔ |
| locales/zh_CN.json | 192167 | 189212 | 189212 | 2955 | ✔ |

  本机这 10 个文件 CR 数为 0(`git ls-files --eol` = `i/lf w/lf attr/`,仓库**没有** `.gitattributes`),
  而 GitHub 的 windows runner 系统 gitconfig 是 `core.autocrlf=true` → 结帐成 CRLF,每个 LF 多一个 CR,
  正好等于上表的差值。
- **根因**:漂移守卫对 EOL 敏感,而这批 `.gz` 是在 LF 工作区里用 `windos/tools/pack-core-resources.ps1`
  重打的(335cb3c 那次合并重打了 15 个 `.gz`)。合并前那几次 CI 绿,是因为当时的 `.gz` 是按 CRLF 源打的
  (windos 线在 Windows 上开发),结帐成 CRLF 正好对上。
- **影响**:这是一个**仍然活着**的缺陷 —— 本机 8 轮全绿(因为本机结帐是 LF),但只要把 `windos/**`
  推到 GitHub,`CI` 这个 job 还会照旧红。
- **建议修法(不在本包地盘,交 lead 裁)**:1首选:加 `.gitattributes`,把
  `windos/src/TipCL/Resources/**` 的 `*.json|*.mjs|*.js|*.d.ts` 标成 `text eol=lf`(顺带让 exe 跨机器可复现,
  因为 CRLF 工作区打包会内嵌 CRLF 字节 → exe 哈希随机器变);2备选:让守卫与打包脚本先把 CRLF 归一成 LF 再比
  (`CoreResourcesPackTests.cs` 在本包地盘内,如选这条我可以改);3不该做:在 CI 里绕过守卫。

### 4.2 仍是假设(未定位):`ci.yml` run #231 的 `publish win-x64 (single file) + zip`

- run #231(id `43533747406`,sha `700cd21`)win 侧 job(id `132257566814`)第 4 步
  `publish win-x64 (single file) + zip` = failure,后两步 `hashes` / `upload-artifact` 被 skipped;注解只有
  `Process completed with exit code 1.` 这一条(另加一条 Node 20 弃用警告)。
- 该步骤当时是**四合一**(见 `git show 700cd21:.github/workflows/ci.yml:151-167`):publish → 删非 exe →
  **在包目录里跑 `--smoke` 且失败就 `throw`** → zip。
- 「第二次跑同一步骤 success」这个说法**不准确**:`cc4c39d` 已把这一步拆成 `publish` / `smoke (best effort)` / `zip`
  三步(`git diff 700cd21 cc4c39d -- .github/workflows/ci.yml`),第二次跑的**不是同一步骤**。
- 但有一个新证据可以**否证**「托管 runner 没有交互桌面」:`smoke (best effort …)` 那段脚本在执行
  `$code -ne 0 -or -not $png` 时会写一条 `::warning`;run #232(id `43534797761`)该 job 的注解**只有 Node 20 弃用一条**,
  说明**那次冒烟真的成功了**(exit 0 且有 smoke.png)。所以第一次 exit 1 不是"没桌面"。
- **结论口径**:纯 publish / 纯 zip 在 #232 都是 success,而 #231 的 exit 1 落在那个四合一里(pwsh 步的退出码
  来自最后一条原生命令或 `throw`),**日志匿名读不到**(`…/actions/runs/<id>/logs` 与 `…/jobs/<id>/logs`
  匿名均 403 `Must have admin rights`),所以**第一次为什么 1 仍未定位**;现有拆步 + 降级为 `::warning` 的处置
  已经不会误伤 job。

## 5. R2(本轮不改,只登记)

`windos/src/TipCL/Core/Launcher/Utils.cs`:

- `WriteJson`(`:775`)在 `:782-786` 的注释里承诺"tmp 阶段也要重试 6 轮",但 `MkStemp(...)` 的调用在
  **`:790`**,包裹它的 `try` 从 **`:791`** 才开始 —— `MkStemp` 自己抛的异常**完全绕过重试循环**。
- `MkStemp`(`:753-773`)内部是 `FileMode.CreateNew`(`:763`),唯一的 catch 是
  `catch (IOException) when (i < 9999 && Directory.Exists(path))`(`:768`),**不 catch `UnauthorizedAccessException`**。
- 后果:杀软/Defender 在"新建 tmp"这一步拦截时,`WriteJson` 直接抛,注释里承诺的 6 轮重试 + 直写兜底全部失效;
  真实用户机器上表现为"保存配置/存档偶发失败"。
- 证据:`R30-WP0` 的红轮 trx 里,失败堆栈第一帧就是 `Utils.MkStemp(...) Utils.cs:line 763`,由 `WriteJson` `:790` 调用。
- 建议(产品行为变更,发版前不动):把 `MkStemp` 的调用纳入 `try`;或让 `MkStemp` 把 `UnauthorizedAccessException`
  也当"换个名字重试"。建议在 `docs/RELEASE-DRAFT.md` 的已知问题里登记。
